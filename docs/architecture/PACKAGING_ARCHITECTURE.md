# Physical packaging and media architecture

Task: **14.1 — Packaging Architecture**  
Date: **2026-10-19**  
Inspected application baseline: **91dd2a0**  
Status: **Design complete; implementation remains Tasks 14.2–14.6.**

## 1. Decisions and scope

Preserve the accepted [flat component/presence model](DOMAIN_MODEL.md#7-physical-edition-components-and-templates), specification §§29–31 and 41–47, and the [shared 3D architecture](3D_ARCHITECTURE.md). Templates describe reusable geometry and its artwork surfaces. A release component selects a template and supplies explicit artwork bindings. An owned copy separately records whether that component is present. None of these relationships is inferred from a platform name, cover, photograph, provider result or `hasBox` checkbox.

Finalize four separate concepts: `PackagingTemplate`, `PackagingTextureSlot`, `PhysicalMediaTemplate` and `PhysicalMediaTextureSlot`. Use their already approved dedicated binding relationships. Share the viewer stage, camera, controls, resource ownership and bounded loading; do not introduce a universal template entity, renderer registry, nested inventory or scene editor.

Task 14.1 changes documentation only. It does not add tables, uploads, renderer code, assets, product measurements, public delivery or an interactive editor. Numeric limits and example dimensions below are application policy or synthetic fixtures, not measurements of retail packaging or phone performance.

### Same-template and same-release enforcement

Enforce relational rules in PostgreSQL as well as services:

- Add component candidate keys `(id, packagingTemplateId)` / `(id, physicalMediaTemplateId)` and corresponding slot candidate keys. Each binding has composite FKs to both its component and slot using the same template ID. A binding cannot exist while that component's selected template is null or different.
- Add `(id, gameReleaseId)` to components and `(collectionItemId, gameReleaseId)` to OwnedGame together with the actual presence FKs. Every presence row must match both the copy's selected release and that release's component. Keep unique copy/component and reverse component indexes.
- Check positive expected quantity, nonnegative observed quantity, nonnegative order, kind/template exclusivity and primary-package rules. Do not cap observed quantity at the expected count.
- Restrict template, slot and asset deletion while referenced. Binding rows may cascade only when their component is deletable. Presence restricts component deletion; owned-root deletion cascades its presence without deleting catalog records or assets. Preserve restrictive historical catalog roots.
- The optional future defect/component FK remains deferred work. If added, use the accepted same-copy composite relationship and deferred no-action rule so deleting a copy can remove both dependents.

Live FKs never move into JSON. Store historical IDs in release change snapshots only as history. Do not add unused candidate keys before their FK consumers.

## 4. Template curation and canonical mutations

Start with curated data and narrow administrator operations. A visual template/UV authoring editor is outside this phase. Template drafts can be incomplete and edited with their current concurrency revision. Promotion to READY validates the complete geometry, slots, dimensions and material mapping before committing. Draft/archived templates are not offered for new release assignments; an existing archived assignment remains readable with an archive label, as with other canonical references.

READY freezes the render contract: geometry bytes/asset ID, geometry type, dimensions, slot keys/required flags/targets, UVs and material settings. Any such change creates another row in the same family with a new `revisionNumber`, fresh slot IDs and explicit release reassignment. This freezes no later than the accepted once-referenced rule. Neither a corrected GLB nor a reused slug silently replaces geometry for every release. Template creation retains its curator/time and referenced asset provenance. Camera-only settings and descriptive labels may change under validation and a concurrency revision increment; presentation identity includes that revision.

Promotion is one-way: READY cannot be demoted to DRAFT to bypass immutability. Retire READY revisions by archiving, preserving their family/revision identity. Enforce frozen fields/slots in database mutation guards as well as services. A camera-setting change invalidates dependent component presentation approvals atomically; no stored rendered preview may be treated as current merely because the geometry contract is unchanged.

`materialSettings` chooses a code-owned cardboard/plastic profile with finite roughness/metalness in [0,1] and a bounded base color. It cannot supply shaders, JavaScript, texture URLs, arbitrary material constructors or loader extensions. Camera settings reuse the shared orientation/scale/FOV/distance bounds, adding `package`/`cartridge` presets and explicit front/back directions. Normalization never changes stored physical measurements.

Release assignments/binding edits use the existing catalog-write guard, current administrator reauthorization and expected release/template revisions. Validate selected component, exact template, slots and eligible assets in one short transaction. Replace template and its bindings together; old slot IDs cannot survive a reassignment. A newly selected revision does not automatically copy art by matching slot names: the command must list the reviewed new bindings. Recheck concurrent asset state under the existing asset-lock protocol. Network transfer, GLB inspection and image processing occur outside that transaction; immutable asset IDs/hashes bind the validated input.

With immediate composite FKs, reassignment removes the old binding rows, updates the component template FK, then inserts the reviewed new bindings inside that same transaction. Any validation/write failure rolls everything back; no intermediate unbound state is published.

Increment the release root once and append one complete MANUAL `MetadataChange` under a server-generated `physicalPresentation.<componentId>` path for the changed assignment/binding group. Preserve the existing `includedItems` snapshot for expected-content changes. Record component/template/slot/asset identities and transform versions; retain each source Asset's independent provenance. Equal commands are no-ops; an uncertain retry may acknowledge identical persisted state but must not overwrite a different state at a stale revision. Never mutate or relabel prior enrichment history.

Clear component presentation approval for any renderer-visible component/template/artwork/transform change. Renaming/deleting/changing a component kind must not silently discard bindings or presence. Existing broad release forms must either preserve these new fields through service mapping or route such changes through the explicit reconciliation operation. No delete-and-recreate shortcut for retained component IDs.

## 5. Owned presence and the has-box transition

Render expected contents and observed presence separately. Quantity means interchangeable instances of one identity/artwork, not Disc 1 versus Disc 2. An outer box, inner case and separately illustrated discs are separate flat rows, sharing the owned copy's location. No `parentComponentId`, containment tree or scene arrangement is introduced.

Use presence as the authority when a release has a primary package. Maintain `CollectionItem.hasBox` as an **atomic summary** for compatibility with existing listing/search/filter code: null count → null; zero → false; positive → true. The legacy field remains manually authoritative only when that release has no designated primary package. Do not read one answer on details and another in filters.

- First designation of a primary package is an explicit admin operation. Review the migration of each copy's existing manual answer: true → count 1, false → count 0, null → unknown. If an observation already exists and disagrees, reject the operation until the administrator resolves it; do not overwrite it. The operation owns primary selection, reconciled presence and summary writes atomically.
- With an active primary package, copy forms edit its observed presence. The server derives `hasBox`; an independent submitted checkbox cannot override it. For a new copy, the existing yes/no/unknown input can become an explicit initial primary-package observation, rather than a second editable value.
- Reassigning the primary package requires explicit reconciliation to the new component. Never move an old box observation to a different inner case by ID/name similarity. Preserve old observations, use reviewed existing/new counts for the new primary, and permit an explicit unknown decision. Removing primary designation leaves its last effective summary as the manual fallback; acknowledge that transition explicitly.
- A release correction is not evidence that an owned object changed. Preserve observed quantities when expected counts change; show missing/unknown/surplus against the new expectation. Component removal is restricted while presence exists unless a separate explicit operation reconciles those observations.
- Copy release reassignment must explicitly clear old mappings or provide reviewed mappings/counts to components of the new release, in the same transaction as the OwnedGame FK change. Do not match by name or carry `hasBox` into an unrelated new primary automatically. Copy notes/photos remain with the copy. Cross-release FKs enforce this even if service validation is bypassed.

Use the shared catalog guard before dependent copy locks in stable UUID order, then recheck current authority and revisions before writes. A single-copy presence edit bumps that aggregate once and follows existing publication-reset behavior. Administrative primary transitions check the displayed release revision and affected copy revisions, lock/reload the complete affected set and reject a changed membership/baseline. Changed copy summaries/presence advance each affected copy once and reset its publication. Do not secretly overwrite a copy draft that changed during review.

Keep these primary transitions bounded: at most 1,000 affected copies in one short transaction initially; reject beyond that with an operator migration requirement. Do not partially designate a primary package across pages or add a queue. The first feature migration adds nullable/default fields and preserves legacy answers without automatically assigning a primary package. Activation is the reviewed operation above. Missing presence observations are unknown; a legacy hasBox value is only its manual box summary, never evidence of complete contents.

## 6. Geometry and slot authoring

Use a right-handed scene with +Y up and artwork front facing +Z. Store physical measurements in millimeters and convert once to meters. These conventions align with [glTF coordinates and units](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units). A viewer normalization group can center and uniformly fit the selected piece; it must not scale axes independently to force a model into claimed dimensions.

### First packaging format: closed procedural box

Task 14.2 starts one curated SNES cardboard-box format with a closed rectangular cuboid, not opening flaps or a simulated paper net. Actual dimensions/variant suitability require curator evidence before a real template becomes READY. Do not claim one universal SNES box or invent historical measurements. Use synthetic labelled fixtures while establishing the renderer.

`PROCEDURAL_BOX` creates one segment per axis and six independently addressable faces. Define this mapping in code and test it against pinned Three.js; never discover faces from an arbitrary material-array order at runtime. [BoxGeometry](https://threejs.org/docs/pages/BoxGeometry.html) supplies width/height/depth along X/Y/Z. The inspected Three.js 0.186.1 source orders its groups +X, −X, +Y, −Y, +Z, −Z; the following is GemuKore's explicit semantic mapping:

| Group | Face normal | Template key for first format | Surface width × height | Image right / image up in object space |
| ----- | ----------- | ----------------------------- | ---------------------- | -------------------------------------- |
| 0     | +X          | `EDGE_POS_X` (optional)       | depth × height         | −Z / +Y                                |
| 1     | −X          | `SPINE` (required)            | depth × height         | +Z / +Y                                |
| 2     | +Y          | `TOP` (optional)              | width × depth          | +X / −Z                                |
| 3     | −Y          | `BOTTOM` (optional)           | width × depth          | +X / +Z                                |
| 4     | +Z          | `FRONT` (required)            | width × height         | +X / +Y                                |
| 5     | −Z          | `BACK` (required)             | width × height         | −X / +Y                                |

All six faces exist even if no artwork is bound. The opposite narrow edge is not automatically another spine. `INNER` is unsupported for this closed-box revision; adding an interior needs a separately authored revision/geometry, not a key pointing at an unrelated face. A slot target is `{kind: PROCEDURAL_FACE, face: ...}` plus its expected material name; two slots cannot target the same face.

### Authored packaging and media GLBs

`GLB` slot targets record `{sceneIndex, nodeIndex, meshIndex, primitiveIndex, materialIndex, uvChannel: 0}` plus expected node/material names for authoring diagnostics. Check the exact indexed target belongs to the selected scene and node's mesh/primitive; require usable TEXCOORD_0 and a nondegenerate art region. Reject missing, ambiguous or duplicate targets at readiness. Names are useful diagnostics, not identity: glTF names need not be unique. [glTF indices and names](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#indices-and-names).

Each replaceable artwork primitive has one rectangular normalized UV island, with its slot's physical art width/height declared in millimeters. Different artwork surfaces need distinct primitive/material positions even when the GLB originally shares a material. Two different slots cannot replace the same primitive. No bounding-box image projection, guessed material-name search, UV unwrapping or mesh editing occurs in the application. Use GLTFLoader's source associations to resolve primitives in the pinned loader, accounting for a mesh instantiated by different nodes; verify that resolution when upgrading. Do not rely on generated Object3D names.

Validate authored geometry against declared dimensions before readiness: normalized axes, positive finite bounds, and dimensions within the larger of 1 mm or 2% per axis. This is a curation tolerance, not permission to distort the model. A cartridge/disc/card GLB must include its real silhouette; a disc hole comes from geometry rather than guessed image transparency. Replaceable surfaces contain neutral placeholder material. Missing bindings must never reveal another game's baked-in label. Non-artwork geometry/materials remain authored content and must pass the ordinary asset/profile review.

## 7. Artwork, crop and texture mechanics

Bindings select prepared DISPLAY assets explicitly. A Game cover, personal PHOTO/BOX image or screenshot never becomes a texture automatically. Reject COLLECTION assets for canonical bindings; an administrator who intends to curate a personal scan must explicitly create a separate sanitized CATALOG asset with reviewed provenance. No hotlink, remote fetch or AI artwork generation is part of binding.

Use a versioned binding transform `{schemaVersion: 1, crop: {x, y, width, height}, quarterTurns}`. Crop coordinates are fractions of the auto-oriented DISPLAY image, with origin at its upper-left: finite x/y ≥0, width/height >0, x+width/y+height ≤1, and at least one source pixel in each dimension. `quarterTurns` is an integer 0–3, clockwise in image space. Defaults are the entire image and zero turns. Crop first, rotate second, uniformly contain/center third. Expected aspect comes from the slot's physical art rectangle. No implicit stretch, mirror, full-wrap splitting or destructive cover crop. An atlas requires explicit per-slot crops; the browser does not recognize a paper net.

Build a session-owned opaque neutral-padded artwork canvas for each bound slot. Initial `box-v1`/`gltf-slots-v1` profiles cap its longest edge at 1,024 pixels and never enlarge beyond useful source resolution; reserve its actual output dimensions before allocation. This creates a bounded preview surface without rewriting the original/display asset or pretending it is a new archival scan. Padding must be neutral: clamp-to-edge sampling alone would smear border pixels into unused space. Use opaque base-color replacements initially, with no new custom shader/mask pipeline.

Use one top-left artwork UV convention. Adapt procedural BoxGeometry UVs once (invert its default V coordinate), so they agree with authored glTF slots. Decode the prepared raster without another EXIF rotation or vertical flip, apply crop/turn/contain in the canvas, then use sRGB color maps with `flipY=false`. Do not apply an extra source-color conversion to non-color material maps. The upper-left glTF texture origin is specified in [glTF image coordinates](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#images); sRGB color maps follow [Three.js color management](https://threejs.org/manual/pages/color-management.html).

For ImageBitmap loading, orientation/premultiplication are decode options; changing Texture.flipY afterward does not flip the bitmap. Use explicit `imageOrientation: none` / `premultiplyAlpha: none` for this top-left path, then verify all six labelled faces and cartridge labels in actual browser tests. [ImageBitmapLoader](https://threejs.org/docs/pages/ImageBitmapLoader.html), [Texture flipY](https://threejs.org/docs/pages/Texture.html#flipY).

Parse each GLB into the existing session-owned resource graph. Clone materials per targeted node/primitive position before replacing a base-color map, even when authored materials are shared. Artwork gets a white color multiplier and the selected validated surface profile; untouched surfaces keep their authored PBR properties. Remove/neutralize any replaceable placeholder map for missing artwork. Track original, cloned and replaced resources until owned teardown so none leak or get disposed while still referenced. Two releases sharing one template must never share mutable materials or texture transforms.

### Ingestion and reference lifetime

The first private slice can explicitly bind existing eligible catalog display images through administrator selection. For uploads into a component, extend the existing catalog target with `includedItem`, permit appropriate image gallery/preview roles, resolve its active parent release, and recheck that release revision at attachment. Upload creates a component gallery use, not a slot binding; the administrator selects the returned DISPLAY asset for a named slot separately. Keep the existing processor, private storage, source retention and recoverable completion semantics.

When authored geometry ingestion is needed, add a distinct typed template-geometry target referencing an existing DRAFT packaging/media template. It requires catalog permission, CATALOG MODEL_3D bytes and the expected template revision, and attaches directly to the template FK. Do not invent a CatalogAsset target or upload against an unrelated release to obtain geometry. Version that upload manifest to describe a direct template attachment instead of pretending every target creates a use row; retain read/retry support for existing v1 manifests. This is a minimal extension of the existing upload service/transport, not another storage pipeline. READY contracts cannot be replaced by upload completion.

Update asset deletion/reference-family checks for template model FKs and both binding families. Removing a binding releases its use, not its source bytes. Preserve immutable AssetDependency lineage and do not delete a shared source because one release stopped using it. File provenance stays on Assets; transform/mapping provenance stays on the binding/template contract.

## 8. Private presentation and shared viewer handoff

Keep `src/components/three/model-viewer.tsx` as the shared lightweight activation shell. Introduce a strict version-2 presentation with a small discriminated content union: existing plain `GLB`, `PACKAGING` or `PHYSICAL_MEDIA`. Existing console production can remain on v1 during the transition; use an explicit validated adapter rather than accepting optional catch-all properties. Code samples here are design shapes, not new application exports.

An assembled description contains one component ID, template identity/contract revision/concurrency revision, one procedural geometry description **or** model resource, ordered slot targets with eligible image resources and transforms, validated settings, static poster, provenance labels and completeness state. No raw settings/metadata bag, arbitrary URL, object key, original filename, audit actor, private component note or executable scene description enters shared rendering code.

The authenticated feature request identifies `{collectionItemId, componentId, expectedCopyRevision, expectedReleaseRevision}`. The service obtains current `private.read`, validates that this GAME copy still selects the component's release, then reads the component/template/slots/bindings/assets and presence in one repeatable-read snapshot. Server code decides readiness and fallback; React never queries the database or resolves authorization. A normal private viewer can read; catalog mutation permission is not needed to rotate an object.

Private resources use the existing same-origin `/api/media/private/<assetId>` route with current grant/READY checks on every request. The assembled DTO additionally proves correct component/slot relationships. Use verified MIME, length, dimensions and immutable asset identity for each resource. Hash the copy/release revisions, component/template contract and concurrency revisions, sorted bindings/transforms/asset identities, renderer profile and settings into the presentation key. This is staleness identity, not a delivery credential. Reopen/retry/switch obtains fresh authorization; no shared descriptor or private-byte cache.

Prefer an explicitly selected component. A default may select the designated primary package, otherwise the first suitable MEDIA component in stable order; label which piece is shown. Only one piece occupies the existing Canvas. Switching box → Disc 1 → Disc 2 ends the old session before loading the next. Never render `quantity` duplicate meshes or mount one Canvas per component.

Create only the files used by the authorized slice, not empty scaffolding.

## 9. Loading, budgets and cleanup

Reuse the established `interactive-v1` limits and lifecycle. One assembled component has an aggregate 12 MiB transfer cap, including an optional GLB (still ≤8 MiB) and separate images (initially ≤2 MiB each). All actually delivered bytes count; deduplicate identical immutable resource IDs within the session only. A binding to the same source with a different crop may need another output texture allocation even though it shares one fetch. Reject contradictory descriptors for one resource ID.

Retain at most eight content textures, 2,048-pixel source edges, eight million admitted image pixels, 64 MiB estimated texture memory including mipmaps, 24 MiB geometry, 200,000 rendered triangles, 80 draw calls, 256 nodes and 64 materials. Count embedded GLB images/maps, separate resources, cloned materials, composited outputs and repeated mesh instances as applicable. Reserve space for each live decode/composite before allocation and release scratch bitmaps promptly; do not count only final visible maps. Output profiles and source lifetimes must fit the combined envelope. Stage environment resources retain their existing separate bounded ownership. An over-budget original stays available under normal private download policy; this feature does not weaken upload acceptance or silently rewrite originals.

Separate artwork accepts prepared PNG/JPEG/WebP only, with bounded header/dimension inspection before decode, actual MIME/size checks, and decoded-dimension verification. WebP is necessary for existing DISPLAY outputs; AVIF/SVG/animated images are outside this first preview profile. Preserve PNG/JPEG-only embedded glTF validation and no external/data URIs, required extensions, decoders, animation, skinning or morph targets. No library default image loader may bypass the common authorized/bounded fetch path. Inspect source bytes before handing them to the decoder.

One component uses one overall 60-second transfer deadline, caller cancellation and a maximum of two simultaneous transfers. Do not give each of eight files a fresh full deadline or hold a database transaction during fetch/decode. Show aggregate verified received/total bytes only when known; preparation is an indeterminate state. Reuse the 10-second decode/first-frame watchdog and late-generation fencing; the watchdog cannot interrupt synchronous JavaScript.

Extend `ModelResources` to own procedural geometries, cloned materials, newly composed textures/canvases, source ImageBitmaps, GLB dependencies and late completions. Dispose a texture separately from its material, close owned bitmaps once, and release canvas backing stores only after no live texture/session needs them. Native fullscreen reuses the session; dialog replacement or component switch closes it. Do not enable useLoader/useGLTF global caching, THREE.Cache or browser persistent storage. Three.js resource ownership/disposal is explicit, including resources created outside React; [Three.js cleanup](https://threejs.org/manual/pages/cleanup.html) and [R3F object lifecycle](https://r3f.docs.pmnd.rs/api/objects#disposal) explain the underlying behavior.

Keep lazy loading, demand rendering, zero grid canvases, stable DPR/pixel cap, keyboard/touch/HTML controls, reduced motion, offscreen pauses and static fallback. No shadows/postprocessing/refraction/opening animation is added to make a box appear more elaborate. Existing physical Android coverage remains waived/unverified; extended Safari native-memory retention remains a recorded limitation in [3D performance evidence](../performance/3D_PERFORMANCE.md), not resolved by this design.

## 10. Public eligibility and source boundaries

Phase 14 starts private. Component presentation approval and an artwork source are not publication by themselves. Phase 18 needs a separate server projection and the existing contextual public delivery contract; it must check global enablement, copy publication, field/settings gates, component approval, READY DISPLAY resources, asset content/rights approval and applicable immutable lineage for every geometry, texture and poster request. Known IDs/private descriptors never bypass these checks.

A private template referencing an ORIGINAL GLB is not public-ready. Public use requires an explicitly curated template revision with eligible reviewed DISPLAY geometry, including its embedded images, and explicit component reassignment/approval. Never resolve an arbitrary derivative or fall back to a private original at runtime. This design adds no public derivative generator or public route. Procedural geometry has no model file but still needs an approved component presentation and eligible delivered artwork.

Future rendered thumbnails retain fixed RENDER_INPUT dependencies for every contributing geometry/artwork input and renderer/settings identity, plus independent content review. No thumbnail job, model/texture CDN, shared cache, signed-read lifetime, provider import or automatic publication is introduced. Preserve manually entered metadata and Asset source/licensing information; a front scan does not prove back/spine art or distribution permission.

## 11. Worked examples and acceptance cases

**One shared box, different games:** Release A and Release B each have their own PACKAGING component selecting one `snes-cardboard` template revision. A binds its FRONT/BACK/SPINE assets; B binds different assets. Neither changes the template to acquire its title/artwork. Closing A and opening B creates isolated materials/textures. No source from A can remain on B after cancellation or a failed fetch.

**Multiple independently illustrated pieces:** a collector release has Outer box, Inner case, Disc 1 and Disc 2 as four flat components. Both discs can select the same media template and bind different DISC_ART assets. All have expected quantity one. A copy may record outer box 0, inner case 1, Disc 1 unknown, Disc 2 one. Only the designated primary package determines its has-box summary; the inner case does not automatically stand in for the missing outer package. One selected piece is rendered at a time.

**Synthetic UV fixture:** use dimensions 120 × 170 × 25 mm, with labelled FRONT/BACK/SPINE/TOP/BOTTOM/EDGE_POS_X images, top-left arrows, asymmetric corner colors and readable text. These are deliberately not asserted SNES measurements. Verify front/back are upright, every outward normal and edge orientation matches §6, the spine is not mirrored, crop/turn is explicit, and wrong-aspect art contains neutral margins. For media, use an original synthetic labelled model, not downloaded commercial artwork.

Required implementation evidence:

- Database: kind/template checks, cross-template and cross-release FK failures, duplicate binding/presence/primary rejection, restrictive shared-asset deletion, stable component IDs, draft/archived assignment policy, immutable READY contracts and explicit revision changes.
- Transactions: current role/revocation checks after lock waits; stale release/template/copy conflicts; all-or-nothing assignment/bindings/history/approval reset; upload retry into stale/deleted draft; no-op/exact retry behavior; rollback on a dependent write failure.
- Presence: null versus zero versus surplus; initial true/false/unknown migration; contradictory existing observation rejection; primary reassignment/removal; new-copy initialization; release reassignment; expected-count corrections; search/filter/detail summary consistency and published-copy reset.
- Math/assets: all six faces/axes and unit conversion, GLB index resolution with duplicate names/shared meshes/materials, UV0 checks, crop boundaries/quarter-turns/contain, missing placeholder neutralization, WebP/header/decode limits, cumulative transfer/pixel/GPU allocation and source reuse with differing transforms.
- Browser: real authorized image delivery → assembly → render; two releases sharing geometry with distinct art; multiple discs selected serially; no pre-activation 3D bytes/context; absent/unknown/missing-art labels; cancellation/late results/context loss; original console viewer regressions; 320px/dark/zoom/keyboard/touch/reduced motion; repeated switch/open/close resource cleanup. Physical-device claims require actual measurements.

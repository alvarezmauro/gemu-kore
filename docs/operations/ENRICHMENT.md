# Enrichment service

Task 13.2 implements the [enrichment architecture](../architecture/ENRICHMENT_ARCHITECTURE.md). Task 13.3 adds the private preview and optional manual-flow entry controls described below. No enrichment runs automatically during manual catalog or collection saves.

## Setup

Deploy the checked-in Prisma migration through the project's normal database deployment process before invoking enrichment. It adds workflow tables, immutable payload/decision constraints and the optional unique suggestion link on metadata history. Tests deploy it only to disposable PostgreSQL; implementation verification does not migrate the personal database.

Structured lookup uses the existing optional [IGDB configuration](GAME_METADATA.md). Provider construction is lazy; missing configuration produces a retained `NOT_CONFIGURED` failure without preventing startup or manual saves. Restart after changing credentials. No additional dependency, secret, worker or AI vendor is required.

Web evidence retrieval and AI synthesis currently report explicit skipped-stage reasons. Structured facts retain `PROVIDER` origin and no confidence score. Rating acceptance lacks typed catalog storage; images require validated private ingestion. Both remain explicitly ineligible. Broad Game evidence cannot establish a physical edition: release runs currently support only an explicitly selected reference mapping.

## Private operations

`src/server/services/enrichment/index.ts` exports the runner and review operations. `src/features/enrichment/actions.ts` provides authenticated server actions with sanitized failures. Inputs are strict validated objects. Server code obtains a trusted access context from `requirePrivateAccess`; never construct one from submitted identity/role fields.

| Operation                          | Input and behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `enrichmentRunner.start`           | `{target: {kind, id}, expectedRevision, requestKey, query}` with kind `game` or `release`. Generate one UUID request key per intended lookup. An existing unambiguous accepted IGDB Game mapping fetches directly; otherwise retain one search page. Repeating identical intent with the same key returns the existing run. A different actor or intent cannot reuse the key.                                                                                                     |
| `enrichmentRunner.selectCandidate` | `{runId, expectedRunVersion, externalId}`. Select a returned candidate explicitly, even if there is only one. Fetch resumes the same logical attempt. A different match needs a new run.                                                                                                                                                                                                                                                                                          |
| `getEnrichmentReview`              | `{runId}`. Return a private canonical target summary, candidate/field choices, proposals, sources, manual-replacement requirements, unavailable capabilities and receipt. Expired active leases become failed; changed baselines invalidate pending proposals.                                                                                                                                                                                                                    |
| `prepareEnrichmentReview`          | `{runId, expectedRunVersion, fields, trailerExternalId?, companyBindings?}`. Freeze one validated whole-group proposal per selected supported field. Trailer selection and existing local developer-company bindings are explicit. A unique accepted company mapping can resolve a developer automatically. Unresolved developers are ineligible. Equal values produce no suggestion. Choices cannot be changed after publication; equivalent retries return the retained review. |

Every selected populated manual or unknown-origin field needs its own acknowledgement ID. One short transaction validates current grants, revisions and relations, writes selected catalog groups, increments the root once, records linked immutable provider history, finalizes decisions and stores a receipt.                                                              |

Exact repeats are harmless.                                                                                                                                                                                                                                                                                                                                           |

Older repeated retry commands return retained state without another provider request.                                                                                                                                                                        |

Runner retrieval methods also accept an optional trusted `AbortSignal` argument. `createEnrichmentRunner(() => provider)` supplies the neutral adapter seam used by deterministic tests; actions use the production composition point.

Editors may create and manage their own runs. Administrators may review/manage any run, but a start key always belongs to its original requester. Only a current administrator with both `enrichment.accept` and `catalog.manage` may apply. Permissions are reloaded after the shared catalog guard. Viewers and public callers have no run access. Responses contain no owned-copy notes, photos, locations, defects, credentials or raw provider responses.

## Failure and recovery

One active request has a 45-second deadline, propagated into the existing bounded provider adapter. Waiting for candidate selection holds no connection or lease. External calls run outside database transactions. Publication uses the remaining transaction budget; a timed-out publication rolls back and records only a fenced failure during bounded cleanup. A 90-second persisted lease handles abandoned processes; authorized reads/retries recover expiry. A late response must still match its operation generation and current grant before it can be retained.

Admission serializes in PostgreSQL with the existing catalog write guard: one active operation per original requester and 20 new intentions per requester per hour. Retries remain subject to active and three-attempt limits. There are at most 20 search candidates, 32 suggestions, 512 KiB normalized provider output and 1 MiB combined workflow snapshot budget. No live provider response is trusted without runtime validation.

Cancellation in another server process cannot immediately abort that process's socket; database fencing prevents publication, and the adapter/request deadline bounds its lifetime. There is no background job or automatic recovery scheduler. If authority is revoked during retrieval, publication is denied; an administrator can inspect/recover the retained lease later.

A stale or archived root, changed parent identity dependency or changed mapped company cannot be accepted. Pending proposals become `CONFLICT`; start a new intentional review rather than changing the old baseline. Partial acceptance also conflicts the remaining pending proposals. Rejections remain final.

After an ambiguous apply response, repeat the exact token and suggestion selection or read its receipt. The stored receipt is returned before checking the old root revision, even after a subsequent manual edit; the same batch never applies twice. A mixed/different accepted selection requires a new review. All selection writes and history roll back together on failure.

Targets and accepted source history are retained. Actor deletion may null attribution while preserving sources, decision times and receipts. No automatic purge, publication or media approval occurs. Replacing a trailer clears its public approval. Future public attribution must use a dedicated projection; private run DTOs are not public data.

## Verification

Deterministic adapter fixtures exercise search, selection, freeze, acceptance, no-ops, provenance, permission revocation, conflicts, rollback, retries, quotas, cancellation, lease recovery and malformed output. Integration checks use isolated PostgreSQL and no live provider credentials. Existing catalog/playtime/trailer/manual-creation regressions verify the shared write paths; desktop/mobile browser smoke tests verify the production build and private-entry behavior. The preview is covered by component checks and authenticated desktop/mobile browser flows. Browser setup explicitly clears live metadata credentials and seeds retained evidence through the neutral service adapter in an isolated fixture process.

## Preview workflow

After selecting a game and release in Add game, use **Review game metadata** or **Review release reference**. Each opens `/app/enrichment` in a new tab, retaining the add-game page's notes, defects, files and selected identity. The same entries appear on saved game-copy details for editors and administrators with active canonical identities. Viewers have no entry or review access.

1. Find metadata, or follow a retained run link. Repeating an uncertain start uses its original request key. A new lookup is an explicit separate intention.
2. Choose a provider game after comparing its title, classification, platforms, first release year and excerpt. A game match does not confirm a physical edition.
3. Choose supported field groups. Select the trailer explicitly and optionally bind provider developers to existing active companies through the private narrow company lookup. Preparing freezes those choices; missing or unsupported evidence remains ineligible.
4. Compare **Current value**, **Suggested value**, **Source** and **Confidence**. Source pages open as links; remote media is not fetched or attached. Confidence is “Not provided” for structured evidence. Descriptions are rendered as plain text, never HTML.
5. Editors may ignore choices or copy the retained review link for an authorized administrator. Other editors cannot open someone else's review. No notification or message is sent automatically. Administrators can Apply per field, Apply selected or Apply all; populated manual/unknown-origin fields require individual acknowledgements. Ignore selected/all records final rejections without catalog writes.
6. A receipt confirms committed changes. Remaining pending choices become conflicts. Refresh review after an uncertain response to inspect retained decisions; start a new lookup for stale/conflicting choices.
7. Return to the original Add game tab and select **Refresh catalog choices**. This reloads the same platform, game and release and returns to My copy, preserving personal values and photo files. Continue through Review again before saving. The server independently rejects a stale save even if the user skips refreshing. Nothing retargets or automatically resubmits the copy.

The review offers explicit retry, status refresh and cancellation when a retained operation permits them. An initial synchronous lookup may take up to 45 seconds before a run response is available; its controls remain busy during that request. Closing a tab does not promise immediate remote cancellation. Manual saving never depends on finding or accepting enrichment.

The page uses the shared warm panels and functional controls, stacked comparisons at narrow widths, explicit status text, visible labels, keyboard actions and focused errors. It adds no animation dependency; reduced motion keeps a complete static experience. Private page metadata is generic and excluded from indexing. It introduces no public run endpoint or provenance displays on public pages.

Task 13.4 adds [current source labels, retained administrator history and private media attribution](PROVENANCE.md). Manual replacement checks also treat a field as unknown when its current value no longer matches the latest recorded source.

Task 13.5's [phase review](../architecture/ENRICHMENT_REVIEW.md) rejects ambiguous candidate/trailer IDs and makes retained evidence limits visible before selection or acceptance. The **Evidence limitations** panel uses fixed explanations for incomplete search/identity context and limited or invalid supported sections; it does not change which facts can be accepted, relax acknowledgements or fetch new evidence on reload.
